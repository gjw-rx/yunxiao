# 云效 Agent 类 Claude Code 架构演进规划

&gt; 本文档基于现有基础架构（`01-VSCode插件开发指南.md`、`02-服务集成方案.md`、`03-实施步骤拆解.md`），规划从"基础对话"演进到"类 Claude Code 智能助手"的完整路径。

---

## 一、核心问题回答

### 问题：整个框架层都需要在插件开发，远程只是调用模型？

**答案：不是。推荐采用"混合编排"架构。**

三种方案对比：

| 方案                          | 决策与循环在哪          | 工具执行在哪                                  | 评价                                |
| ----------------------------- | ----------------------- | --------------------------------------------- | ----------------------------------- |
| A. 云端全编排 + 本地纯执行    | 云端 Agent（LangGraph） | 云端工具 + 本地工具                           | 改动小，但需双向协议                |
| **B. 混合编排（推荐）** | 云端 Agent 决策         | **云端工具 + 本地工具并存**，按路由分发 | 兼顾复用与本地能力                  |
| C. 本地全编排 + 云端只调模型  | 本地 ReAct 循环         | 全部本地                                      | 放弃云端已有 Agent 框架，重复造轮子 |

**推荐方案 B 的核心判断依据**：

1. 云端已有 Agent 框架（skill/mcp/tool 装配、LangGraph checkpointer、记忆），放弃它意味着把这套东西用 TS 在插件里重写一遍，违反 DRY 与 YAGNI。
2. 但本地文件操作、终端、diff、git、代码索引这些操作，**绝不能让云端执行**——既不安全（用户工作区不在云端），也低效（每次传文件内容浪费 token）。
3. Claude Code 本质就是这个架构：模型在 Anthropic 云端决策，工具在本地 CLI 执行，工具结果回传云端继续推理。

## 二、架构职责划分

### 2.1 云端服务职责（已有 + 扩展）

| 已有职责                        | 新增职责                                                             |
| ------------------------------- | -------------------------------------------------------------------- |
| Agent 装配（skill/mcp/tool）    | 工具调用路由：识别`execution_site` 字段，本地工具调用通过 SSE 下发 |
| LangGraph Agent 循环（决策）    | 接收本地工具执行结果，续流                                           |
| LLM 调用                        | 工具结果注入对话历史                                                 |
| 记忆（checkpointer）            | 会话内工具调用历史归档                                               |
| 云端工具执行（搜索/知识库/MCP） |                                                                      |
| SSE 流式推送                    |                                                                      |

### 2.2 本地插件职责（核心新增）

| 模块                 | 职责                                                                |
| -------------------- | ------------------------------------------------------------------- |
| **工具注册表** | 声明本地工具 schema（名称、参数、权限要求）                         |
| **工具执行器** | 执行本地工具，返回结构化结果                                        |
| **工具协议层** | 与云端协商工具调用，处理`tool_call` 事件 + 回传 `tool_result`   |
| **文件操作**   | read/write/list/search/move/delete，带工作区根解析与路径安全校验    |
| **代码智能**   | 符号搜索、引用查找、诊断查询（基于 VSCode Language API）            |
| **Diff 引擎**  | patch 生成、应用、回滚、可视化对比视图                              |
| **终端执行**   | 受控 shell 执行（白名单/审批/超时）                                 |
| **Git 集成**   | status/diff/commit/branch，基于`vscode.git` API 或 `simple-git` |
| **代码索引**   | 本地符号索引（ctags/tree-sitter/ripgrep），向云端提供上下文检索     |
| **审批网关**   | 写操作、终端执行前向用户确认（类 Claude Code 的"允许/拒绝"）        |
| **会话状态机** | 维护 session 内的工具调用流水，处理中断/重试/续流                   |

### 2.3 数据流（一次完整工具调用）

```
用户输入"把这个函数改成异步"
  ↓
插件 -> POST /message/stream
  ↓
云端 Agent 推理（思考: 需要先读文件）
  ↓ SSE: {type:"tool_call", tool:"fs.read_file", args:{path:"..."}, call_id:"c1", site:"local"}
  ↓ SSE 流暂停（或自然结束当前 chunk）
插件执行 read_file -> 文件内容
  ↓
插件 -> POST /tool_result {session_id, call_id:"c1", status:"success", result:"<文件内容>"}
  ↓
云端 Agent 继续推理（思考: 需要改写）
  ↓ SSE: {type:"tool_call", tool:"code.edit", args:{path, old, new}, call_id:"c2", site:"local"}
插件 -> 审批网关 -> 用户确认 -> 应用 diff -> 展示对比视图
  ↓
插件 -> POST /tool_result {session_id, call_id:"c2", status:"success", result:"已应用"}
  ↓
云端 Agent 继续推理 -> 多个 content 事件 -> 流结束
```

## 三、协议扩展（关键设计）

### 3.1 SSE 事件类型扩展

在现有 `content` / `thought` / `tool_start` / `tool_end` 基础上新增：

| type                | data 结构                                                               | 含义                                     |
| ------------------- | ----------------------------------------------------------------------- | ---------------------------------------- |
| `tool_call`       | `{call_id, tool, args, site:"local"\|"cloud", require_approval?:bool}` | 工具调用请求                             |
| `tool_call_batch` | `{calls: tool_call[]}`                                                | 批量并行调用（可选优化）                 |
| `plan`            | `{steps: string[]}`                                                   | Agent 计划展示（类 Claude Code 的 todo） |
| `progress`        | `{message, current, total}`                                           | 进度提示                                 |

**说明**：

- 保留 `tool_start` / `tool_end` 用于**云端工具**的执行展示（云端已执行完才推送）。
- 新增 `tool_call` 用于**本地工具**调用请求。

### 3.2 工具结果回传接口（云端新增）

```
POST /api/agent/invoke/tool_result
Body: {
  session_id: string,
  call_id: string,
  status: "success" | "error" | "cancelled",
  result: string,           // 成功时的输出（文本或 JSON 字符串）
  error?: string,           // 失败原因
  metadata?: {              // 可选元数据
    affected_files?: string[],
    diff?: string,
    duration_ms?: number
  }
}
Response: ApiResponse<{ done: boolean }>
```

云端收到后，将 `{role:"tool", tool_call_id, content}` 注入 LangGraph 状态，触发下一轮推理，并继续以 SSE 推送（或返回 `done:true` 表示会话结束）。

### 3.3 续流模式选择

云端 Agent 循环到本地工具调用时，**SSE 流应当自然结束**（推送 `tool_call` 后 yield `end` 事件），等本地工具结果通过 `/tool_result` 回传后，**云端主动重新发起一次内部 `ainvoke`**，并通过新的 SSE 流推送后续事件。

这种"流中断 + HTTP 回传 + 内部续流"模式的优势：

- 不需要 WebSocket 双向连接
- 复用现有 SSE 解析逻辑
- 失败/超时易处理（HTTP 请求有明确响应码）
- 多客户端协议一致

前端只需把"用户消息发送"和"工具结果回传"都视为触发新一轮 SSE 流的入口。

- 定义 `ToolCall` 类型：`{call_id, tool, args, site, require_approval}`

- 保留 `content` / `thought` / `tool_start` / `tool_end` 处理

**为什么**：现有 `handleSseBlock` 只处理 4 类事件，需可扩展

**依赖**：Step 1.1

**风险**：Low

#### 步骤 1.3：工具注册表骨架

**做什么**：

- 实现 `register(schema, executor)`

**为什么**：工具发现与路由的基础

**依赖**：Step 1.1

**风险**：Low

#### 步骤 1.4：实现首个本地工具 read_file

**文件**：`src/tools/fs/readFile.ts`

**做什么**：

- 实现 `fs.read_file` 工具
- 含路径解析（调用 `pathGuard`）
- 含大小限制（默认 1MB）
- 含二进制检测（通过文件扩展名或 MIME）
- 继承 `BaseTool` 基类

**为什么**：验证端到端协议，先做只读工具（无需审批，风险最低）

**依赖**：Steps 1.1, 1.3, 1.5

**风险**：Low

#### 步骤 1.5：路径安全守卫（CRITICAL）

**文件**：`src/tools/fs/pathGuard.ts`

**做什么**：

- 实现工作区根解析（从 `vscode.workspace.workspaceFolders` 获取）
- 实现 `..` 越界检测（规范化后检查是否在工作区根下）
- 实现符号链接解析（可选配置是否跟随）
- 实现绝对路径规范化（Windows/Unix 路径差异处理）
- 实现敏感文件检测（`.env`、`.git`、`credentials.json` 等，需额外审批）

**为什么**：**CRITICAL**——所有文件工具的安全前提，防止路径遍历攻击

**依赖**：None

**风险**：High（安全关键）

**单测重点**：

- `../../../etc/passwd` 应被拦截
- 工作区外绝对路径应被拦截
- 带符号链接的路径应正确处理
- Windows `\` 与 Unix `/` 都应支持

#### 步骤 1.6：会话状态机

**文件**：`src/core/sessionManager.ts`

**做什么**：

- 维护 `sessionId -&gt; {pendingToolCalls, history, abortController}` 映射
- 处理 SSE 流的多次中断与续流
- 管理工具调用的 pending/running/success/error 状态
- 实现超时与取消逻辑

**为什么**：工具调用模式下，一次用户输入会触发多轮 SSE 流（每轮含工具调用），需要状态机协调

**依赖**：Steps 1.1, 1.2

**风险**：Medium（状态正确性是难点）

#### 步骤 1.7：工具结果回传接口

**文件**：`src/protocol/toolCallProtocol.ts`

**做什么**：

- 封装 `POST /tool_result` 调用
- 含重试逻辑（指数退避，最多 3 次）
- 含超时逻辑（默认 30s）
- 含错误映射（网络错误、服务错误的友好提示）

**为什么**：续流的关键回传通道

**依赖**：Step 1.1

**风险**：Medium（依赖云端新增接口，需联调）

#### 步骤 1.8：扩展 AIClient

## 九、与云端团队需对齐的协议要点

在 Phase 1 启动前，必须与云端团队明确以下协议：

### 9.1 SSE `tool_call` 事件格式

```json
{
  "type": "tool_call",
  "data": {
    "call_id": "c1",
    "tool": "fs.read_file",
    "args": { "path": "src/extension.ts" },
    "site": "local",
    "require_approval": false
  }
}
```

### 9.2 续流策略

- 推送 `tool_call` 后，SSE 流自然 end
- 本地回传 `/tool_result` 后，云端重新 `ainvoke` 续流
- 续流时，历史对话应包含 tool 消息

### 9.3 `/tool_result` 接口契约

见 3.2 节。

### 9.4 本地工具 schema 上报

- 方案 A：创建会话时一并上报（`POST /session` body 增加 `local_tools` 字段）
- 方案 B：单独接口 `GET /api/agent/tools/local` 拉取
- **建议选方案 A**，减少一次 round trip

### 9.5 工具命名空间

- 本地工具统一前缀：`fs.` / `code.` / `terminal.` / `git.`
- 避免与云端工具冲突

### 9.6 审批结果表达

- 用户拒绝时本地返回 `{status:"cancelled", error:"user denied"}`
- 云端 Agent 应据此调整策略（询问替代方案，而非死循环重试）
