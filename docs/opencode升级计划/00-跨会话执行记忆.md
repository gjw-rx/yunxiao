> 用途：后续每个实现会话先阅读本文件，再只处理一个 change。本文是 explore 阶段的结论快照，不替代具体 OpenSpec change。

> 对标源码：`sdks/yunxiao-agent/docs/opencode源码/opencode`

## 一、总体判断

当前系统已经具备 LangGraph 云端编排、SSE 流式交互、VSCode 本地工具、审批、路径守卫、代码智能、终端和 Git 能力；主要差距不在“工具数量”，而在 Agent harness 的可靠性：

- 云端原先缺少稳定的请求级 Run 身份、幂等准入和恢复索引；LangGraph checkpoint 与 AgentTrace 已分别承担 Graph 状态和观测记录。
- 计算生命周期与 SSE 连接耦合，断线、重启、多实例和重复提交缺少统一恢复语义。
- 插件有本地运行状态，但缺少可恢复 RunStore、sequence replay 和非幂等工具执行日志。
- 授权、文件版本、预算和 UI 时间线还没有统一到 run 级别。

目标不是复制 OpenCode 的技术栈，而是形成“云端编排与记录 + 插件受策略约束的本地执行”。

## 三、后续分批实施路线

### P1：云端持久 Run Harness（本次会话已落地）

这是云端必须补齐的核心能力，建议单独开一个 session/change，不与 UI 或插件大重构混做。

#### 已落地的数据与状态边界

- 只保留一张轻量 `AgentRun`：`run_id`、`session_id`、`client_request_id`、`status`、`last_checkpoint_id` 和时间字段。
- `run_id` 与 `(session_id, client_request_id)` 有唯一约束；`session_id`、`last_checkpoint_id` 和 Trace 关联均为逻辑关联，不使用数据库外键或级联。
- `AgentTrace` 增加可空 `run_id`、`tool_call_id`，继续复用既有模型回复、工具调用、token 和耗时记录。
- 删除/不新增 `AgentStep`、`AgentToolCall`、`AgentRunEvent`；LangGraph checkpoint 是 Graph 节点、pending task、interrupt、消息和恢复位置的唯一事实来源。
- 初始 `ainvoke`、初始流式执行及 `Command(resume=...)` 均显式使用 `durability="sync"`。
- 生产 PostgreSQL checkpointer 初始化失败时，invoke/stream/resume 统一 fail-closed；只有显式 `memory` 开发模式允许内存 checkpointer。

#### 服务边界

- 已新增独立 `RunRepository` / `RunService`：幂等创建或回读、状态转换、checkpoint 指针、`pending/running` 恢复扫描。
- `RunService` 不保存 Graph Step，也不自动推进 Graph；Graph 状态仍由 LangGraph checkpointer 读取。
- 现有 `InvokeService` 只增加持久化 guard、同步 durability 和 checkpoint+消息历史状态读取，不新增事件时间线。
- v1 接口保持兼容；`client_request_id` 接入命令 API、计算与 SSE 解耦、同 thread 分布式互斥属于后续 change。

#### 已确认与后置的可靠性语义

- 本次已确认：请求级 Run 幂等基础、生产 checkpoint fail-closed、同步 durability、checkpoint 当前/最终状态读取。
- 本次未实现：SSE 断线后的 sequence replay、工具结果 execution receipt、resume lease、startup 自动推进和同一 `thread_id` 的跨实例互斥。

#### P1 本次验收

- Run/Trace/持久化 guard 与 LangGraph 调用测试已通过；Ruff 已通过。
- 本地环境缺少 `psycopg`，完整 LangGraph backend 回归未能执行；安装项目依赖后需补跑全量测试。
- 精确 sequence replay、重复 tool result 防重、跨实例互斥和 startup recovery 保留为后续 change。

### P2：插件恢复与本地执行安全

- `RunStore`：按 session/run 保存事件、状态和 cursor。
- sequence gap 检测、replay、workspaceState cursor。
- 非幂等本地工具 execution journal，支持 `unknown` 状态，禁止盲目重放。
- scoped approval：workspace、tool、资源模式、有效期。
- `code.edit` 的文件版本贯穿 read → preview → apply。
- 范围读取、cursor、搜索结果和终端输出 artifact 化。
- 结构化 argv 命令满足策略时自动放行。

P2 依赖 P1 的稳定 RunEvent/sequence/resume 协议；不要在 P1 完成前自行设计一套插件私有 replay 协议。

### P3：预算与 UI

- run 级 step、wall-clock、token、输出大小和重复调用预算。
- 文本 delta 按 100–250ms 或 4KB 批量持久化，避免逐 token 写数据库。
- Webview 时间线只消费 RunStore，不自行推断运行状态。
- 最后再做可访问性、真实 VSCode E2E 和性能基准。

## 四、推荐的独立会话拆分

每个新 session 只选择一个 change：

1. `add-agent-run-persistence`：轻量 AgentRun、AgentTrace 逻辑关联、checkpoint authority、同步 durability 和生产 fail-closed（已实现并待归档）。
2. `add-run-event-sequencer`：Run 行锁、sequence、事件写入事务。
3. `separate-run-compute-from-subscription`：RunService、StreamProcessor、v1/v2 API。
4. `add-run-idempotency-and-recovery`：client request 幂等、tool result hash、lease、startup recovery。
5. `add-plugin-run-store-replay`：插件 RunStore、gap/replay、workspace cursor。
6. `add-local-tool-execution-journal`：非幂等工具 journal 和 unknown 状态。
7. `add-scoped-approval-and-file-versioning`：范围授权和 code.edit 版本链。
8. `add-run-budgets-and-timeline`：预算、delta batch、RunStore 时间线。

## 五、每个新会话的启动模板

开始实现前固定回答：

1. 本 session 只负责哪个 change？
2. 明确修改哪些目录，明确不修改哪些目录？
3. 依赖哪个已完成 change 或协议？
4. RED 测试是什么？
5. 完成标准是什么：类型、Lint、单测、集成测试、迁移检查或 E2E？
6. 是否需要新增/更新 OpenSpec？

结束时记录：变更文件、验证命令、未解决风险、下一 session 的前置条件。默认不要自动 commit，除非用户明确要求。

## 六、明确不应提前做的事

- 不要先做 Webview 大改造，再补 Run 事实来源。
- 不要把持久 Run、事件序列和恢复逻辑继续塞进 `InvokeService`。
- 不要用 `max(sequence)+1` 生成事件序号。
- 不要把 duplicate ack 当成正常 SSE 完成。
- 不要让插件在没有云端 replay/lease 语义时自行猜测运行已经完成。
- 不要把 OpenCode vendored 源码直接纳入插件 TypeScript 编译或运行时。
