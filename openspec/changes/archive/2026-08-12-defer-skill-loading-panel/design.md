## Context

当前扩展激活会在注册 `yunxiaoAgent.chatView` 之前执行并等待 `syncSkills()`；该函数按配置顺序遍历项目、用户级及自定义目录并读取每个 Skill 文件。目录规模较大时，VS Code 无法解析侧栏 Webview Provider，用户因此看不到任何加载反馈。

`ChatViewProvider` 已在初始化早期构造，但其会话管理器和设置依赖会在后续装配完成后注入。React Webview 首次挂载后会立即发送 `webviewReady`、请求斜杠命令并创建会话。因此仅提前注册 Provider 而不引入就绪协议，会使 Webview 在依赖未装配时触发无效操作。

## Goals / Non-Goals

**Goals:**

- 在首次 Skill 同步进行时即可注册并打开侧栏对话 Webview。
- 用与当前 VS Code 主题一致的居中插件图标和加载文案提供明确反馈。
- 运行时和 Skill 均就绪后，在同一已打开 Webview 中无刷新地启动现有会话初始化流程。
- 保持 Skill 同步的目录顺序、去重、串行重载及现有设置页刷新语义。
- 通过中文结构化日志记录初始化阶段与耗时。

**Non-Goals:**

- 不减少 Skill 文件的读取量、解析逻辑或改变缓存策略。
- 不增加新的用户配置项、后台常驻进程或外部依赖。
- 不改变模型配置、会话持久化、工具审批或 Skill 的执行语义。
- 不在本变更中实现初始化失败后的手动重试入口。

## Decisions

### 1. 提前注册 Provider，首次 Skill 同步改为受控后台任务

扩展先完成创建 Provider、注册基础工具和 `SkillRegistry`，并注册侧栏 Provider 与打开命令；首次 `syncSkills()` 不再 `await` 阻塞这些入口。其 Promise 仍由扩展持有，并复用现有 `syncChain` 串行化机制，避免首次加载与设置变更、安装后的刷新互相覆盖。

在需要完整运行时的依赖（路由、Agent Loop、会话管理器、设置依赖）装配完成后，后台任务完成 Skill 同步并发布最终就绪状态。这样不把尚未可用的服务暴露给用户操作。

备选方案是在同步开始前构建并缓存 Skill 元数据，或改为按需扫描。前者仍会阻塞首开且增加缓存失效复杂度；后者会改变 Skill 可用性与设置页语义，超出本次视觉启动优化范围。

### 2. 使用显式运行时就绪消息，Webview 自行延后业务初始化

Host 维护 `initializing`、`ready`、`failed` 三态，并在收到每个 `webviewReady` 时回传当前状态；状态变化时也主动推送。React 应用始终先完成消息订阅和握手，但只有收到 `ready` 后才请求斜杠命令并创建首个会话。重复的 ready 消息必须幂等，确保隐藏后恢复或重建 Webview 不会丢失状态或创建多个会话。

Host 同时在未 ready 时拒绝或忽略会话创建、消息发送、历史读取和 Skill 相关请求，作为 UI 防护之外的边界，避免旧 Webview 或手工消息绕过前端状态。

备选方案是只在 HTML 中输出静态启动页，完成后重写 Webview HTML。该方案会重新加载脚本、增加闪烁，并使 Host/Webview 生命周期分散；使用现有 React 应用和消息桥接能保留主题与可访问性实现。

### 3. 加载态以独立 React 视图呈现，不渲染可交互聊天内容

运行时不是 `ready` 时，聊天根组件只渲染居中品牌图标、加载文案或失败提示。加载页不触发首个会话创建，不提供消息输入、会话菜单和 Skill 选择；`failed` 状态展示明确错误信息而不是无限旋转。加载样式使用 VS Code 主题变量、现有图标资源与可访问文本。

备选方案是保留完整聊天页面并禁用局部控件。它会在尚无会话时暴露不完整的界面，也不能满足用户希望先看到清晰图标加载页的视觉目标。

### 4. 复用已有 Skill 刷新出口并在完成后刷新订阅者

首次后台同步成功后调用既有 `refreshSlashCommands()`；设置页的请求仍以 `SkillRegistry` 当时快照为准。来源切换、目录保存与 ZIP 安装继续等待各自的 `syncSkills()` 调用完成后再返回刷新结果，不与启动任务并发修改注册表。

## Risks / Trade-offs

- [Webview 早于依赖装配发送业务消息] → 以 Host 三态守卫所有依赖会话或 Skill 的消息，并只让 UI 在 ready 后发起初始业务请求。
- [Webview 在状态推送前重建] → `webviewReady` 必须返回当前状态，且 ready 初始化做幂等处理。
- [初始同步失败导致无反馈] → 捕获后台任务异常、记录含耗时的错误日志，并向已打开和后续打开的 Webview 推送 failed 状态与简明错误提示。
- [首次同步与设置变更发生竞态] → 初始同步与后续重载均进入现有串行队列；变更完成后仅依据最终注册表刷新 UI。
- [加载页与 VS Code 主题不协调] → 仅使用现有主题变量和扩展图标，不硬编码背景或前景色。

## Migration Plan

1. 先增加 Host/Webview 就绪协议和加载视图，并以单元测试覆盖状态转换与消息守卫。
2. 调整 `extension.ts` 的注册与首次同步时序，让首开在同步期间进入 loading 状态。
3. 执行现有编译与测试，并手动验证大 Skill 目录下的首次打开、同步完成后的自动可用和设置页重载。
4. 若发生回归，恢复对首次 `syncSkills()` 的等待与现有即时 Webview 初始化行为；该变更不涉及持久化数据或迁移。
