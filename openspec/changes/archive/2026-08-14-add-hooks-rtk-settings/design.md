## Context

云效 Agent 当前通过 `AgentLoop` 驱动一次运行，并由 `ToolRouter` 完成本地工具的参数校验、安全审计、审批和执行。终端工具 `terminal_exec` 在工具内部执行命令白名单分类和审批；设置页已提供模型、Skill、MCP 和使用情况四类内容。现有 `EventBus` 是同步事件通知，不具备异步 Hook 的顺序、超时、参数转换和故障隔离能力。

RTK 是外部 CLI：它通过 `rtk rewrite <command>` 返回可替代的命令，并在该命令实际执行时压缩 CLI 输出。RTK 不应改变云效的工具权限、审批或安全边界；它仅作为已由用户启用的本地优化程序使用。

## Goals / Non-Goals

**Goals:**

- 建立只包含四种基础事件的异步 Hooks 运行时：`session_start`、`pre_tool_call`、`post_tool_call`、`session_end`。
- 允许受信任的 `pre_tool_call` Hook 改写工具参数，并确保最终参数仍接受现有校验、安全审计和审批。
- 以 RTK Adapter 验证这一扩展点，仅优化 `terminal_exec.command`。
- 在现有设置页中以一致的交互和视觉层级管理 Hooks 与 RTK。

**Non-Goals:**

- 不加载用户编写的任意脚本、npm 包或远程 Hook，不建立插件市场和供应链安装流程。
- 不自动安装、升级 RTK，也不调用 `rtk init` 修改 Claude、Codex 或其他 Agent 的配置。
- 不改写现有 `simple-git` 本地 Git 工具、文件工具、代码工具或 MCP 工具的执行后端。
- 不承诺 RTK 压缩率等同于模型 API 费用降幅，也不在第一版复制 RTK 的全量统计和 TOML 配置。

## Decisions

### 1. 新建异步 HookManager，而非复用 EventBus

`HookManager` 维护内置 Hook 注册表、已保存的 Hook 配置和一次调用的执行轨迹。它按优先级串行执行同一阶段的 Handler，并为每次 Handler 设置有界超时；每个 Hook 的失败被记录后隔离，不得击穿 AgentLoop。

四个事件的语义固定为：

- `session_start`：每次 `AgentLoop.run` 开始时派发，载荷只含会话、运行和工作区元数据。
- `pre_tool_call`：每次本地工具完成初始参数校验后、实际执行前派发。
- `post_tool_call`：每次本地工具生成并经过共同结果治理后的结果派发，只读观察结果。
- `session_end`：每次 `AgentLoop.run` 以成功、失败或取消结束时派发。

这里的 session 事件以一次 Agent run 为粒度，而非等待用户关闭 Webview；这样可以在当前会话生命周期模型中可靠地实现开始与结束配对。

备选方案是扩展现有 `EventBus`。不采用它，因为异步执行、超时、参数替换和可见的失败策略会将通知总线变成难以维护的策略执行器。

### 2. 将参数转换限制在受信任的 Pre-tool Hook

`pre_tool_call` Handler 分为观察/阻断和受信任转换两类。第一版只注册扩展自带的转换器；转换器只能提交替换后的 `args`，不能修改 `tool`、`call_id`、权限、注册来源或工作区范围。Router 对替换后的参数重新执行 schema 与手写校验。

同一阶段先运行转换器，再运行阻断器，二者都按稳定优先级执行。显式阻断会取消工具调用；异常、超时或无效转换不会产生替换，也不会阻断原调用。这样 RTK 的优化失败遵循 fail-open，而安全策略仍能通过显式阻断生效。

备选方案是允许所有 Hook 执行任意 Shell 脚本或修改整个 ToolCall。该方案会扩大本地代码执行与权限绕过面，超出第一版范围。

### 3. Router 保存原始与最终调用，并对两者执行安全判断

Router 在初始校验后创建不可变的原始调用快照。预工具转换产生最终调用后，Router 重新校验最终参数，并对原始和最终调用均运行 `SecurityAudit`；任一被拒绝即不执行。审批和终端白名单需要同时获得原始与最终命令：白名单和用户意图基于原始命令判断，实际执行与审批显示基于最终命令，并清晰展示“原始 → 改写后”。

这避免了两类问题：改写后的 `rtk ...` 前缀使原本白名单命令被误判为未知命令，以及转换器用最终参数绕过原始危险命令检查。

备选方案是先审批原始命令、再转换。这会使用户批准的内容与实际执行内容不一致，因此不采用。

### 4. RTK Adapter 通过原生命令改写接口集成

RTK Adapter 仅匹配 `terminal_exec` 且要求 Hooks 与 RTK 均已启用。它以 `spawn(rtkPath, ['rewrite', command], { shell: false })` 调用二进制，命令始终作为单个 argv 参数传递。仅当子进程在超时前成功返回非空改写结果时替换 `command`；无匹配、缺少二进制、版本/能力检测失败、超时、非零退出或非法输出均保留原命令。

Adapter 不向模型注入“请使用 rtk”的提示词，不调用 `rtk init`，也不对 `git_status`、`git_diff` 等 `simple-git` 工具做工具名改写。RTK 的输出过滤发生在最终命令实际由终端工具执行时。

### 5. Hooks 配置采用“精密运维面板”，而不是通用表单或密集列表

新增版本化 Hooks 配置，保存总开关、RTK 启用状态和可选二进制绝对路径。安装后 Hooks 运行时可用但 RTK 默认关闭，用户必须在设置页显式开启；不存在 RTK 时页面给出状态和配置入口，不自动下载。

Hooks 页面采用克制的原生深色运维面板方向，与现有 VS Code 主题和设置页 token 保持一致，但不把每个 Hook 处理成重复的表格行。首屏按以下阅读顺序组织：

1. 标题区：`自动化控制台` eyebrow、Hooks 标题、简短说明，以及紧凑的运行状态和总开关。
2. 生命周期轨道：将四个事件呈现为可快速扫读的连续节点——会话开始、工具执行前、工具执行后、会话结束；每个节点显示启用 Hook 数量和状态，当前有集成的节点获得有限的强调。
3. 已启用自动化：RTK 作为唯一的主集成卡片，明确其作用范围 `terminal_exec`、状态、启用开关，以及“原命令 → RTK rewrite → 紧凑输出”的简短过程预览。
4. 高级配置：可执行文件路径、重新检测和固定样例测试收纳在可展开区域，避免让一次性配置项压过日常状态；测试成功时仅强调改写前后的命令，不显示或执行完整命令输出。
5. 安全说明：以低权重说明强调“仅改写 terminal_exec；改写失败执行原命令”，不与主操作争夺注意力。

截图中的“钩子列表”适合管理大量第三方 Hook，而第一版只有四类事件和一个内置 RTK 集成。直接复制该密集列表会产生大面积重复的开关、信任标签和空状态，反而遮蔽 RTK 的可用性与安全语义；故不采用。

Host 提供读取快照、保存配置、重新检测和测试改写消息。检测使用 `--version` 与 `rewrite --help` 验证，测试使用固定的无副作用样例 `git status`；页面不执行用户输入的测试命令。实现复用已有设置页的侧栏、字体、按钮、主题变量、卡片边界和响应式滚动，但新增局部的生命周期轨道、状态标签与 RTK 主卡片样式，不引入新设计体系。

## Risks / Trade-offs

- [RTK 不可用或版本不兼容] → 检测状态可见，改写 fail-open，终端保持原行为。
- [转换使审批与执行不一致] → 保留转换轨迹，审计两份命令，审批界面展示原始和最终命令。
- [Hook 延迟拖慢工具调用] → 每个 Handler 设置超时，第一版只提供少量内置 Hook，并记录耗时。
- [RTK 压缩遗漏诊断细节] → 使用 RTK 自身失败输出回退能力；用户可关闭 RTK 后重试原命令。
- [任意 Hook 扩大攻击面] → 第一版只允许扩展内置且受信任的 Hook，外部脚本加载留待后续独立变更。

## Migration Plan

1. 扩展激活时为不存在的 Hooks 配置创建安全默认值：运行时启用、RTK 禁用、未指定二进制路径。
2. 用户在 Hooks 设置页检测并显式启用 RTK 后，后续符合条件的 `terminal_exec` 调用开始改写。
3. 关闭 RTK 或总 Hooks 开关即可立即回退为当前调用路径；不需要删除数据或修改其他 Agent 配置。

## Open Questions

- 第一版不开放外部 Hook 安装；其权限模型、签名校验和沙箱策略将在后续独立提案中确定。
