## Context

聊天 Webview 已迁移为 `src/webview-ui/` 下的 React + TypeScript + Vite 应用。`App.tsx` 负责组合聊天界面，`SessionHeader.tsx` 负责新建会话与历史下拉；当前没有页面路由，也没有设置页。模型配置、Skill 注册与 token 用量均由扩展宿主维护，但本次明确不改变这些后端链路。

设计假设：用户所说的“独立进入一个页面”是指在同一聊天 Webview 中切换为完整设置视图，而不是创建第二个 VS Code WebviewPanel 或打开 VS Code Settings。这能保留聊天状态、避免新增宿主命令，并符合“暂时只实现前端界面”的范围。

## Goals / Non-Goals

**Goals:**

- 在聊天头部提供位于新建会话和历史会话之间的设置入口。
- 用接近参考图信息层级的深色双栏布局提供模型、Skill、使用情况三个可切换分类。
- 让用户能在不丢失当前聊天、输入草稿、流式状态或历史下拉数据的前提下进入和退出设置页。
- 使用现有 React 组件、CSS token 与图标风格实现，不新增第三方依赖。

**Non-Goals:**

- 不读取、保存或同步模型、Skill、用量、账户或任何 VS Code 配置。
- 不增加 Webview 与扩展宿主之间的新消息协议，不修改扩展激活、AgentLoop、SessionManager 或数据存储。
- 不实现费用计算、用量图表、模型切换、Skill 启停或设置持久化。
- 不复刻参考图中与本插件无关的账户、MCP、插件或个性化设置。

## Decisions

### 1. 在 `App` 中使用轻量视图状态，而非引入路由库

`App` 持有一个仅包含 `chat` 与 `settings` 的页面状态，并基于该状态渲染聊天主体或新的 `SettingsPage`。设置按钮和返回按钮仅更新该本地状态；聊天 reducer、会话 ID、消息数据和输入组件保持已挂载或由现有状态恢复。

选择该方案是因为只有两个内部视图且不需要 URL、深链或浏览器历史。备选方案是引入 React Router；它会增加依赖和路由基础设施，无法为本期纯前端展示带来实际收益。

### 2. 将设置页拆为独立组件与样式范围

新增设置页组件（以及必要的共享图标）负责侧栏分类、内容区和返回操作；样式放入 Webview 现有样式体系，复用 VS Code 主题变量和已有 token。内容区采用标题、说明和卡片/行项目的层级，而非把所有 JSX 塞入 `App`。

选择独立组件可避免聊天页面继续膨胀，也让后续接入真实配置时有清晰的承载点。备选方案是将设置 JSX 内联到 `App`；它代码量稍少，但会混合聊天事件处理与设置展示，后续维护成本更高。

### 3. 将模型、Skill 与使用情况建模为静态展示分类

分类导航与内容完全由前端常量定义：模型页展示当前“待接入”配置说明和只读字段样式；Skill 页展示管理能力的占位说明；使用情况页展示本期不统计真实数据的空/占位状态。点击分类只切换可见内容，不会调用 `postMessage`。

选择显式静态状态可避免界面暗示已生效却没有后端支持。备选方案是复用当前聊天收到的模型名或会话 token；这会扩大到数据语义和刷新时机，违背本期不改后端的边界。

### 4. 保持历史会话功能和可访问性契约

设置入口使用按钮语义、清晰的 `aria-label` 与 tooltip；历史按钮及其请求、下拉关闭、打开、删除和回放逻辑不变，只调整其在头部操作组中的视觉顺序。进入设置页时不自动展开或请求历史列表。

选择保持既有消息协议与交互可将回归风险局限在 Webview 视觉层。备选方案是将设置做成新的 VS Code 命令/面板；该方案需要宿主侧注册和生命周期管理，不符合前端优先目标。

## Risks / Trade-offs

- [静态控件被误认为可保存] → 所有值使用只读展示或明确“即将支持/本期仅展示”文案，不展示无效的保存按钮。
- [在小宽度 Webview 中双栏拥挤] → 侧栏采用固定但紧凑宽度，内容区可滚动；在窄视图中保持分类可访问，不隐藏返回入口。
- [聊天视图切换破坏进行中的状态] → 只切换 `App` 视图状态，不重置 reducer、会话 ID 或向宿主发消息；实现时补充组件/状态测试覆盖切换行为。
- [截图风格与用户主题冲突] → 以 VS Code CSS 主题变量和当前聊天 token 为主，参考截图只用于信息层级、留白和深色卡片结构。
