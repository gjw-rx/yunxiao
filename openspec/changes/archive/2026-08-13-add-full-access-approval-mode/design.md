## Context

当前审批由 `ApprovalGateway` 集中处理：路由层对 `write`、`execute` 与 `destructive` 工具调用审批，`code_edit` 和 `terminal_exec` 因为需要 diff 或命令分类而自行调用网关。对话 Webview 的输入工具栏目前只有“+”文件引用按钮；前后端通信已有类型化协议，宿主 `ChatPanel` 已负责接收 Webview 消息。

目标是让用户在输入区快速切换审批策略：默认继续逐次请求批准；启用完全访问后，非删除操作不再因审批中断。该开关不能削弱独立安全边界，例如工作区路径限制、危险命令硬拦截、安全审计和结果治理。

## Goals / Non-Goals

**Goals:**

- 在“+”右侧提供清晰、可访问的审批模式菜单和当前状态提示。
- 将模式持久化到当前工作区，并在 Webview 重建和会话切换后正确同步。
- 为普通变更/执行操作统一自动批准，同时让文件删除和终端删除命令始终需要人工确认。
- 保持现有普通模式、单次允许、持久 scoped allow 与拒绝结果的行为兼容。

**Non-Goals:**

- 不增加云端权限 API、账户级同步或新的外部依赖。
- 不将完全访问模式用于绕过 `SecurityAudit`、`pathGuard`、危险命令拦截、结果脱敏或输出截断。
- 不改变删除操作的既有二次确认语义，也不把已经被硬安全规则拦截的命令改为可执行。
- 不重新设计附件选择、模型选择或现有审批卡片的视觉系统。

## Decisions

### 1. 用工作区级枚举保存审批模式

新增一个本地配置键，值为 `request` 或 `full-access`，默认 `request`。`ApprovalGateway` 通过可注入的模式存储读取它，便于不依赖真实 VS Code 的单元测试；`ChatPanel` 在 Webview 握手和模式变更后发送当前值。

选择工作区级持久化而非仅 Webview 内存，因为完全访问是明确的用户策略，关闭并重新打开面板或新建会话时不应悄然恢复默认值。选择枚举而非布尔值，为界面文案和未来受限模式保留清晰的状态契约，但本次只实现两个值。

替代方案：仅保存到当前会话。它能缩小影响面，但会使用户在正常的面板重建与会话切换中反复设置，和“开启后自动同意”的预期不符。

### 2. 在 ApprovalGateway 的最终提示前做模式决策

所有需要批准的调用继续先经过本地校验、安全审计和工具自身预处理。随后 `ApprovalGateway` 对非删除调用在 `full-access` 模式下直接返回 `allow`，不写入 `sessionAllow` 或 scoped grant，也不触发 Webview/VS Code 提示；日志记录模式、工具和会话 ID。

该位置同时覆盖路由层工具、代码编辑和未知终端命令，避免每个工具各自读取 UI 配置。现有 `request` 模式和 scoped grant 的优先级保持不变。

替代方案：在 `ToolRouter` 中跳过审批。该方案不能覆盖 `handlesOwnApproval` 的 `code_edit` 与 `terminal_exec`，会产生不一致行为。

### 3. 删除操作使用显式分类，不以“非 read”推断

声明为 `destructive` 的工具继续调用 `requestDestructiveApproval`，完全访问不能影响它。终端工具在危险命令硬拦截之后、普通审批之前识别删除意图（至少覆盖 `rm`/`rmdir`、Windows `del`/`erase`、PowerShell `Remove-Item` 和 `git clean`）；命中且未被硬拦截的命令走 destructive 审批路径。

这样“删除命令”在终端的 `execute` 权限中也保留人工确认，而非仅保护已注册为 `destructive` 的文件工具。检测逻辑应由终端安全分类模块提供可测的判定，避免在 UI 或字符串文案中重复正则。

替代方案：所有终端命令都当作非删除自动批准。它会违背删除操作仍需确认的产品承诺。

### 4. 输入区使用弹出菜单并通过协议同步

`MessageInput` 在文件引用按钮之后增加一个按钮，显示当前模式图标与文本；点击后显示两个带说明的单选菜单项。切换发出 `setApprovalMode`，宿主校验枚举、更新配置并广播 `approvalMode`。按钮必须具备 `aria-haspopup`、`aria-expanded`、键盘 Escape 关闭和焦点可达行为；流式回复期间仍允许切换，因为它只影响后续工具调用。

采用宿主为真源而非 `acquireVsCodeApi().setState`：配置持久化、多个 Webview 生命周期和核心审批判断都由扩展宿主统一控制。

## Risks / Trade-offs

- [模式会扩大非删除操作的执行范围] → 通过明显的“完全访问”文案、持久当前状态展示、工作区范围和可即时切回降低误用风险。
- [终端删除命令难以完全靠文本识别] → 覆盖各平台常用删除命令；分类不确定时保持普通审批，现有危险命令规则仍优先拦截。
- [宿主与 Webview 状态短暂不同步] → 以宿主配置为真源，在握手、设置成功和配置变更后下发模式；无效 Webview 请求拒绝并记录日志。
- [现有 scoped/session grant 可能掩盖行为] → 完全访问不新增 grant；关闭模式后立即恢复既有 grant 和提示逻辑。

## Migration Plan

1. 将缺失的配置解释为 `request`，因此现有用户升级后行为不变。
2. 发布时无需数据迁移；写入新配置仅发生在用户主动选择模式时。
3. 若需回滚，实现可停止读取新键；遗留配置对旧版本无影响，重新升级后仍能恢复用户选择。

## Open Questions

- 无阻塞问题。实现时以终端实际支持的 shell 语法补充删除命令测试样本，并保持危险命令硬拦截优先于完全访问。
