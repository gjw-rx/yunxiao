## Context

现有实现以 `contextWindow: 128000`、固定 buffer 和历史消息 token 估算决定压缩；它没有将系统提示词、工具 schema 与模型输出预留一同计入。压缩检查点虽然可让 `HistoryLoader` 忽略旧历史，但重新压缩时仍直接扫描物理历史，且尾部截取不能证明工具调用和结果成对存在。

Hermes Agent 的实现提供了三个可复用原则：以可用输入预算的比例判定、把已有摘要作为增量输入、在发送前清理 `tool_calls`/`tool_call_id` 的孤立关系。本项目必须继续使用已有 `tokenEstimator` 的估算口径，且不引入新的 tokenizer 或第三方依赖。

## Goals / Non-Goals

**Goals:**

- 每个模型档案保存最大上下文 token，缺省为 `262144`。
- 自动压缩以完整请求估算值达到 `(maxContextTokens - maxTokens) * triggerPercent / 100` 为条件，默认 75%。
- 保留近期消息时不切断工具调用链；压缩前再次清理孤立工具结果和无结果的工具调用。
- 手动 `/compact` 可无视自动开关和阈值执行，且不会作为用户文本进入 LLM 历史。
- 所有关键压缩决策写入 `logger`，日志带 sessionId、原因、token 和消息数量。

**Non-Goals:**

- 不替换现有字符除以四的 token 估算器，也不宣称估算值等同提供商账单 token。
- 不物理删除历史消息；继续追加检查点以保持会话可恢复与 UI 历史完整。
- 不在插件 Webview 设置页暴露自动压缩开关、比例或尾部比例。
- 不实现跨模型 tokenizer、摘要加密或新的会话存储格式。

## Decisions

### 1. 用完整请求压力而非历史消息触发

在每次模型调用前，AgentLoop 先构造系统提示词、经 `HistoryLoader` 转换的有效历史和可用工具 schema，再复用 `estimateRequest` 计算请求 token。阈值从模型档案的 `maxContextTokens` 与当前 `maxTokens` 推导，自动触发比例由 VSCode 设置提供。

选择此方案是因为工具 schema 和系统提示词可显著占用上下文。仅扫描 MessageStore 虽更简单，却无法防止实际 API 请求溢出。

备选方案是保留消息数量阈值；予以否决，因为它与模型容量无关，且会在很小的上下文时无谓压缩。

### 2. 检查点表示有效历史，而不是改写持久化消息

`MessageStore` 提供“最新检查点 + 检查点后消息”构成的有效压缩上下文。压缩器将旧摘要与被压缩前段传给模型，成功后仅追加新的 `compaction` 消息，载入器继续从最新检查点开始。

该方式延续当前 append-only 存储和会话 UI 行为，也避免重写 workspaceState 带来的失败恢复风险。

### 3. 按工具调用链选取与清理尾部

尾部选择先从最新消息逆向累积至 `tailPercent` 预算；若候选命中一个 assistant 工具调用或其 tool 结果，则把该次调用及所有对应结果作为一个原子组一起保留。随后以 Hermes 的关系校验规则清理：无对应 `tool_calls` 的 tool 结果删除；缺少结果的 assistant 工具调用删除其无效调用；非孤立消息保持原顺序。

选择两阶段处理可同时应对截取造成的断链和历史中已存在的不完整记录。备选方案是只在转换为 LLM 消息时静默丢弃孤立记录；予以否决，因为压缩检查点仍会保存不合法 tail，日志也无法说明发生了什么。

### 4. 配置归属与即时同步

模型最大上下文是模型能力，因此放入私有模型档案和模型配置页；自动开关与比例是工作区行为，因此只放入 `yunxiaoAgent.compaction.*` 原生 Settings。扩展监听该配置命名空间，在设置变更后更新 AgentLoop；模型切换时同步新的最大上下文。

这满足“模型手动填写”和“压缩参数不走插件配置界面”两个不同配置边界。

### 5. 手动压缩采用独立协议命令

Webview 菜单和精确输入 `/compact` 都向宿主发送 `compactContext`，由 `LocalSessionManager` 进入 AgentLoop。正在生成时拒绝执行，以免在 assistant 工具调用与结果之间生成检查点；手动压缩不使用自动阈值导出的巨大尾部预算，而是只按当前有效历史的尾部保留比例保留近期原文，确保有多条历史时确实生成新的摘要检查点。成功、无需压缩、失败均返回可展示的通知并记录日志。

### 6. 摘要输出预算应覆盖推理和正文

摘要请求的输出预算固定为 `2048` token，而非普通摘要正文所需的 `1024` token。部分推理模型会把推理 token 计入同一输出上限；`1024` 可能在生成正文前已经耗尽。摘要仍只接受正文 `textDelta`，绝不将推理内容写入检查点；若仍只有推理内容，失败日志会携带推理字符数和输出预算，供定位模型或后端设置。

## Risks / Trade-offs

- [粗略估算与提供商 tokenizer 有偏差] → 通过默认 75% 留出余量，并把完整估算值写日志以便调参。
- [单条工具结果大于尾部预算] → 整条工具调用链仍原子保留；摘要负责压缩更早内容，不能发送残缺配对。
- [摘要模型失败] → 不追加检查点、不改变有效历史，记录错误并让当前请求按原流程处理或报告失败。
- [旧模型档案没有新字段] → 读取时回填 `262144`，保存后持久化新字段，避免升级阻塞。

## Migration Plan

1. 新模型字段读取时使用默认值，现有档案无需迁移脚本。
2. 新增 VSCode Settings 并停止读取旧压缩阈值配置；旧 Settings 保留但无行为影响，避免破坏用户 settings.json。
3. 发布后观察 Output Channel 中的 `[上下文压缩]` 日志，确认请求压力和压缩结果。
4. 回滚仅需恢复旧扩展版本；历史检查点仍为既有 `compaction` 消息结构，可被旧载入器读取。
